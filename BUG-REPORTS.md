# Bug Reports — Budget Tracker

Все баги ниже были реально найдены в ходе code review проекта и воспроизведены
в актуальной на тот момент версии `budget-tracker.jsx`. Каждый впоследствии
исправлен — статус и коммит-эквивалент (описание правки) указаны в отчёте.
В списке нет придуманных или гипотетических багов — только то, что
реально воспроизводилось.

Формат: Severity (Critical / High / Medium / Low), Steps to Reproduce,
Expected, Actual, Root Cause, Fix, Status.

---

## BUG-001 — Удалённая категория оставляет «осиротевшие» расходы

**Severity:** High
**Status:** ✅ Fixed
**Component:** Категории / Расходы

**Steps to Reproduce:**
1. Создать категорию «Игры».
2. Добавить расход 500 ₽ в категории «Игры».
3. Открыть Настройки → Категории → удалить «Игры».

**Expected:** Расход либо блокирует удаление категории, либо явно
переносится в «Без категории», оставаясь видимым и понятным.

**Actual:** Категория исчезала из списка и из графика, но запись
с `category: "c-игры-id"` оставалась в `expenses` без изменений.
Сумма продолжала учитываться в общем `totalSpent`, но не отображалась
ни в одной строке разбивки по категориям — деньги «пропадали» из UI,
хотя фактически всё ещё считались потраченными.

**Root Cause:** `handleDeleteCategory` удалял категорию из `categories`,
но не обновлял `expenses`, ссылающиеся на неё по `id`.

**Fix:** При удалении категории все расходы с этим `category`
переводятся в `category: null`, что рендерится как «Без категории»
(уже существующий fallback в `catLabel`/`catColor`). Диалог подтверждения
теперь явно предупреждает об этом.

## BUG-002 — Форма добавления расхода может ссылаться на уже удалённую категорию

**Severity:** High
**Status:** ✅ Fixed
**Component:** Категории / Форма добавления записи

**Steps to Reproduce:**
1. В форме «Новая запись» выбрать категорию «Игры».
2. Не отправляя форму, открыть Настройки → удалить «Игры».
3. Вернуться к форме и нажать «Добавить».

**Expected:** Категория в форме автоматически переключается на
существующую после удаления выбранной.

**Actual:** `form.category` продолжал хранить id удалённой категории.
Отправка формы создавала новый расход, ссылающийся на несуществующую
категорию — по сути тот же дефект, что и BUG-001, но воспроизводимый
даже без уже существующих расходов.

**Root Cause:** Состояние формы не синхронизировалось с изменением
списка категорий.

**Fix:** `handleDeleteCategory` при удалении дополнительно проверяет
`form.category` (и `newRecCategory` в форме регулярных операций) и
переключает их на первую оставшуюся категорию, если они указывали на
удалённую.

## BUG-003 — Двойной commit при Enter в полях редактирования суммы

**Severity:** High
**Status:** ✅ Fixed
**Component:** Редактирование бюджета категории / цели

**Steps to Reproduce:**
1. Кликнуть по сумме бюджета категории, чтобы начать редактирование.
2. Ввести новое значение.
3. Нажать Enter (не кликая мимо поля).

**Expected:** Значение сохраняется один раз.

**Actual:** Поле имело одновременно `onKeyDown` (вызывал commit по Enter)
и `onBlur` (вызывал тот же commit при потере фокуса). Enter в некоторых
сценариях приводил к обоим срабатываниям подряд, что при включённом
подтверждении действий (`confirmActions: true`) могло дважды открыть
диалог подтверждения на одно нажатие клавиши.

**Root Cause:** Два независимых обработчика вызывали одну и ту же
side-effect-функцию без координации между собой.

**Fix:** `onKeyDown` для Enter теперь только вызывает `blur()` на поле;
единственная точка, которая коммитит значение — `onBlur`. Дополнительно
добавлена обработка Escape (отмена редактирования без сохранения) через
ref-флаг, который гасит следующий вызов commit от программного `blur()`.

## BUG-004 — Несогласованная валидация суммы между созданием и редактированием

**Severity:** High
**Status:** ✅ Fixed
**Component:** Валидация форм

**Steps to Reproduce:**
1. Попробовать создать расход с суммой `0` — форма отклоняет.
2. Отредактировать существующий расход, поставив сумму `0`.

**Expected:** Одинаковое поведение validation в обоих случаях.

**Actual:** Создание: `if (!amt || amt <= 0) return;` — 0 запрещён.
Редактирование: `if (isNaN(val) || val < 0) return;` — 0 разрешён.
Один и тот же тип данных (сумма транзакции) имел два разных правила
в зависимости от того, через какую форму его меняли.

**Root Cause:** Валидация была продублирована в двух местах вручную,
без единого источника истины.

**Fix:** Введена единая функция `validateAmount(raw, { allowZero })`.
Суммы транзакций (создание и редактирование) — `allowZero: false`.
Суммы бюджета категории и накоплений по цели — `allowZero: true`,
так как 0 там осмысленное значение («лимит не задан»).

## BUG-005 — Отсутствие проверки структуры данных после `JSON.parse`

**Severity:** High
**Status:** ✅ Fixed
**Component:** Storage / Импорт

**Steps to Reproduce:**
1. Вручную положить в storage-ключ приложения валидный JSON вида
   `{"categories": "hello", "wallets": []}`.
2. Перезагрузить приложение.

**Expected:** Приложение обнаруживает некорректную структуру и
откатывается к дефолтным данным (или следующей по счёту версии storage),
не падая.

**Actual:** `JSON.parse` не бросает исключение на валидном, но неверном
по структуре JSON. Код сразу шёл в `p.categories.map(...)`, что могло
привести к рантайм-ошибке, так как `"hello".map` не существует.
Тот же риск был в обработчике импорта JSON-файла.

**Root Cause:** Проверялась только валидность JSON, но не форма данных.

**Fix:** Добавлена `isValidStoredShape(p)`, проверяющая, что
`wallets`/`categories`/`expenses` — массивы, а `settings` (если есть) —
объект. При несовпадении форма считается повреждённой, выбрасывается
исключение и код переходит к следующему шагу миграции (или к дефолтным
данным). Та же проверка применена к `handleImportFile`.

## BUG-006 — Дата через `toISOString()` может съезжать на сутки

**Severity:** Medium
**Status:** ✅ Fixed
**Component:** Дата по умолчанию в форме добавления записи

**Steps to Reproduce:**
1. Установить локальный часовой пояс восточнее UTC (например, UTC+5).
2. Открыть приложение между полуночью и временем UTC-сдвига
   (например, в 01:00 локального времени при UTC+5, когда в UTC ещё
   22:00 предыдущего дня).
3. Проверить дату, подставленную по умолчанию в форму.

**Expected:** Дата — «сегодня» по локальному календарю пользователя.

**Actual:** `new Date().toISOString().slice(0, 10)` возвращает дату в UTC,
которая на несколько часов около полуночи не совпадает с локальной.
Пользователь в такой момент получал вчерашнюю дату вместо сегодняшней.

**Root Cause:** `toISOString()` всегда работает в UTC независимо от
часового пояса устройства.

**Fix:** `todayISO()` переписан на локальные `getFullYear()`/
`getMonth()`/`getDate()`.

## BUG-007 — Молчаливые ошибки валидации

**Severity:** Medium
**Status:** ✅ Fixed
**Component:** Все формы добавления (расход, кошелёк, категория, цель,
регулярная операция)

**Steps to Reproduce:**
1. Оставить поле «Название» пустым в форме добавления кошелька и
   нажать «Создать».

**Expected:** Пользователь видит сообщение о причине отказа.

**Actual:** Форма просто ничего не делала — `if (!name) return;` без
какой-либо обратной связи. Пользователь мог решить, что кнопка не
работает.

**Root Cause:** Валидация была реализована как ранний `return`
без UI-сообщения.

**Fix:** Каждая форма получила локальный `*Error`-стейт с понятным
текстом («Введите название кошелька», «Сумма должна быть больше 0» и
т.п.), который отображается под формой и сбрасывается при следующей
попытке ввода.

## BUG-008 — Переименование категории в пустую строку

**Severity:** Medium
**Status:** ✅ Fixed
**Component:** Настройки → Категории

**Steps to Reproduce:**
1. Открыть Настройки → Категории.
2. Полностью стереть название существующей категории в поле
   переименования.
3. Кликнуть мимо поля.

**Expected:** Пустое название не сохраняется — либо блокируется с
сообщением, либо откатывается к предыдущему значению.

**Actual:** Поле было напрямую забинжено на `categories` и коммитило
каждое нажатие клавиши, включая промежуточное пустое состояние. Итоговая
категория могла остаться без названия — в списке отображалась только
цветная точка.

**Root Cause:** Отсутствие черновика (draft) — состояние коммитилось
посимвольно без финальной валидации.

**Fix:** Поле переименования теперь работает с локальным черновиком
(`categoryLabelDrafts`) и коммитит значение только на `blur`, с
проверкой на пустоту и на дубликат имени.

## BUG-009 — Гонка асинхронных сохранений в storage

**Severity:** Medium
**Status:** ✅ Fixed (частично — см. Notes)
**Component:** Persistence layer

**Steps to Reproduce:**
1. Быстро внести несколько независимых изменений подряд (добавить
   расход → сразу изменить бюджет категории → сразу переименовать
   кошелёк), не дожидаясь визуальной паузы между действиями.

**Expected:** В storage в итоге оказывается самый свежий снэпшот
состояния.

**Actual:** Каждое изменение стейта запускало собственный
`await window.storage.set(...)`. Поскольку это независимые промисы,
при неудачном порядке завершения более старый вызов теоретически мог
завершиться позже нового и переписать данные устаревшим снэпшотом.

**Root Cause:** Отсутствие координации между параллельными
асинхронными записями одного и того же ключа.

**Fix:** Запись в storage дебаунсится (~400 мс простоя после
последнего изменения), что на практике схлопывает серию быстрых
правок в один-единственный write с самым актуальным состоянием.
Дополнительно введён id-guard (`saveIdRef`), который игнорирует
результат уже устаревшего (не последнего запущенного) вызова записи.

**Notes:** Это снижает вероятность гонки для типичного
однопользовательского сценария (быстрый ввод, пачка правок), но не
даёт строгой гарантии в экстремальных случаях (например, параллельная
работа с одним и тем же кошельком в двух вкладках). Полное решение
потребовало бы версионирования состояния на стороне storage — вне
рамок текущей итерации, зафиксировано как техдолг.
